# Update documentation

Update only documentation affected by an implemented, verified change. Create
a required document only when verified behaviour is missing. This skill may
edit `docs/UserGuide.md`, `docs/DeveloperGuide.md`, `docs/diagrams/`, and
rendered diagrams generated by an existing project workflow.

Do not edit product code, tests, specifications, reflections, logs, build
configuration, `.gitignore`, Git history, GitHub state, or external issues.
Do not install dependencies or documentation tooling without approval.

## Truth and stop conditions

Use this precedence when determining current behaviour:

1. Verified implementation and test/acceptance evidence.
2. Approved issue and acceptance criteria.
3. `specs/ProductSpecification.md`.
4. `specs/MP1-requirements.md`.
5. Routed references in `references/course-reference-map.md`.
6. External examples.

Project sources determine MoneyMap behaviour. External references guide quality
and modelling only. If the issue, specification, implementation, tests,
release status, or evidence materially conflict, do not edit: report every
conflicting source, the affected documentation, the exact conflict, and the
decision needed from the user. Never document prototypes, planned features,
source-only inferences, or unreleased behaviour as available functionality.

Before editing, identify the target issue or release, acceptance status,
changed implementation and Git diff, available verification evidence, and
unrelated working-tree changes. If the target or release status is unclear,
stop and ask for clarification.

## Required reading and scope

Read `AGENTS.md`, `specs/MP1-requirements.md`, `specs/ProductSpecification.md`,
the applicable issue and acceptance criteria, existing User and Developer
Guides, affected diagram sources and images, and only the routed references
that apply. Record references actually read.

| Change affects | Update or inspect |
| --- | --- |
| setup, launch, workflows, validation, errors, SGD/money examples, persistence, backup, import/export, accessibility instructions, screenshots, supported features | User Guide |
| commands, Java/JavaFX requirements, architecture, dependencies, domain, persistence, non-obvious implementation, tests, limitations, recovery, acknowledgements | Developer Guide |
| user-testable behaviour | Developer Guide manual-testing appendix |
| relationships, interactions, state transitions, deployment, or architecture | Relevant diagram only when it materially clarifies the change |
| any change | Inspect both guides for stale cross-document claims; edit only affected files |

## Workflow

1. Read the required project sources and applicable routed references.
2. Inspect implementation, tests, commands, evidence, guides, diagrams, image
   paths, and the Git diff.
3. Classify relevant claims as `Verified`, `Partially verified`, `Unverified`,
   or `Blocked`; do not present the last two as available behaviour.
4. Apply the scope table and stop for any material conflict.
5. Edit only affected sections. Keep the User Guide user-facing and task-based;
   keep the Developer Guide technical, top-down, and maintainer-oriented;
   preserve unrelated content and avoid duplicating code or explanations.
6. Verify claims, commands, links, paths, examples, screenshots, diagrams, and
   manual-testing instructions. Use non-mutating Gradle, test, compiler,
   documentation, link/path, and diagram checks where available.
7. Re-read changed files, inspect the final diff, and report the result.

## Guide and diagram rules

The User Guide must accurately cover affected current user-visible behaviour
for peer testers, including setup, launch, workflows, validation, errors,
formatting, persistence, recovery/import/export, accessibility instructions,
examples, and supported or unsupported features. Do not include internal
classes or unverified behaviour; avoid unnecessary screenshots.

The Developer Guide must accurately cover affected commands, Java/JavaFX
requirements, architecture and dependency direction, domain/persistence
decisions, non-obvious implementation details, actual test commands, diagrams,
limitations, recovery, and acknowledgements. Keep it top-down. It must contain
an `Instructions for Manual Testing` appendix or clearly equivalent heading;
update it for user-testable changes with important inputs and expected outcomes
without duplicating the User Guide.

Acknowledgements must link and describe supported reuse of ideas, code,
documentation, diagrams, assets, libraries, or examples. Do not invent them.

Use diagrams only when they materially clarify a relationship, interaction,
state transition, deployment arrangement, or architectural decision. For an
affected diagram, check its abstraction level, relevant detail, relationships,
dependency direction, sequence accuracy, arrow usage, layer/tier distinction,
and caption. `.puml` files are canonical; check image and Markdown paths.
Regenerate images only through an existing workflow. Do not install rendering
tools; report rendering limitations.

## Evidence and report

Classify evidence as follows:

- `Verified`: passing tests, successful execution, or observed manual acceptance
  directly supports the claim.
- `Partially verified`: evidence covers only some relevant paths.
- `Unverified`: inferred from source or specification.
- `Blocked`: verification was prevented by an environment or project limit.

A successful FXML/resource smoke test does not prove visual correctness,
complete interaction behaviour, or accessibility.

Report files and sections changed, why they were affected, implementation/test/
acceptance evidence, commands and outcomes, references read and their effect,
diagram regeneration status, conflicts, remaining manual verification, omitted
unverified claims, and limitations. If nothing is affected, report that and
the evidence without editing. Do not commit, push, modify GitHub, or declare
documentation correct without verification.
